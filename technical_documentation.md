## 1. Введение

### 1.1 Назначение документа

Настоящий документ является официальной технической документацией программного комплекса **Task.AI** (далее — «Система»). Документ предназначен для технических специалистов, осуществляющих развертывание, сопровождение и дальнейшую разработку Системы.

Документ регламентирует:
- архитектурные решения, принятые при разработке Системы;
- требования к программному и аппаратному обеспечению;
- порядок установки и ввода Системы в эксплуатацию;
- механизмы управления данными и их валидации.

### 1.2 Область применения

Система предназначена для автоматизации процесса планирования учебной деятельности студентов. Программный комплекс обеспечивает:

- **Интеллектуальный разбор задач** — преобразование произвольного текстового описания учебной задачи в структурированную запись с использованием API Google Gemini;
- **Расстановку приоритетов** — автоматическое определение уровня важности и срочности задачи посредством модели искусственного интеллекта на основе матрицы Эйзенхауэра;
- **Визуализацию задач** — отображение сформированных задач на доске в виде карточек с цветовой индикацией приоритета;
- **Календарное планирование** — привязку задач к конкретным датам-дедлайнам с отображением в интерактивном календаре;
- **Управление шагами выполнения** — декомпозицию каждой задачи на подзадачи (шаги) с возможностью отметки их выполнения.

Система ориентирована на использование в браузерном окружении как клиентское single-page приложение (SPA). Персистентность данных обеспечивается средствами браузерного хранилища `localStorage`. Взаимодействие с внешними сервисами ограничено обращениями к Google Generative AI API.

## 2. Требования к системе

### 2.1 Программные требования (среда разработки и сборки)

| Компонент | Минимальная версия | Рекомендуемая версия |
|---|---|---|
| Node.js | 18.0.0 | 20.x LTS или выше |
| npm | 9.0.0 | 10.x или выше |
| Git | 2.30.0 | Последняя стабильная |

> [!IMPORTANT]
> Использование Node.js версий ниже 18.0.0 не гарантирует корректную работу инструментов сборки. Поддержка версий ниже LTS-статуса не осуществляется.

### 2.2 Требования к браузеру клиента

Система функционирует в современных браузерах с поддержкой стандарта ES2020 и Web API `localStorage`. Минимальные поддерживаемые версии:

| Браузер | Минимальная версия |
|---|---|
| Google Chrome | 90+ |
| Mozilla Firefox | 88+ |
| Microsoft Edge (Chromium) | 90+ |
| Safari | 14+ |

Браузер Internet Explorer не поддерживается.

### 2.3 Доступ к внешним сервисам

Для обеспечения функциональности ИИ-разбора задач необходим:

- Активный API-ключ для **Google Generative AI (Gemini API)**;
- Сетевой доступ к эндпоинту: `https://generativelanguage.googleapis.com`.

API-ключ вводится конечным пользователем через интерфейс Системы и сохраняется в `localStorage` браузера. Передача ключа на сторонние серверы, кроме официального API Google, не осуществляется.

## 3. Архитектурные решения

### 3.1 Обоснование выбора технологического стека

#### 3.1.1 React 19

Библиотека **React** выбрана в качестве основы пользовательского интерфейса по следующим основаниям:

- Компонентно-ориентированный подход обеспечивает модульность и повторное использование элементов интерфейса;
- Механизм виртуального DOM (`Virtual DOM`) минимизирует количество операций прямого обращения к реальному DOM, что повышает производительность перерисовки интерфейса;
- Хуки состояния (`useState`, `useEffect`) предоставляют декларативный механизм управления локальным состоянием компонентов без необходимости подключения внешнего менеджера состояния (что оправдано для Системы данного масштаба).

#### 3.1.2 Vite 8

Инструмент сборки **Vite** применяется вместо устаревших альтернатив (Create React App, Webpack) по следующим причинам:

- Использование нативных ES-модулей (`ESM`) обеспечивает запуск сервера разработки без предварительной сборки всего проекта, что сокращает время холодного старта;
- Встроенная поддержка Hot Module Replacement (HMR) обеспечивает мгновенное отражение изменений кода в браузере без полной перезагрузки страницы;
- Использование `esbuild` и `Rollup` на этапе production-сборки обеспечивает высокую скорость компиляции и оптимальный размер итогового бандла.

#### 3.1.3 Tailwind CSS 3

Фреймворк **Tailwind CSS** применяется в данном проекте на уровне конфигурации (`@tailwind base/components/utilities` в `index.css`). В основных компонентах интерфейс конструируется посредством инлайн-стилей (`style`-атрибутов) с использованием предопределённой дизайн-системы на базе пастельной цветовой палитры. Такой подход обеспечивает полный контроль над визуальным оформлением без зависимости от утилитарных классов.

#### 3.1.4 date-fns

Библиотека **date-fns** подключена в качестве вспомогательного инструмента для операций с датами. В текущей реализации основные операции форматирования дат (получение дня, месяца, года) выполняются посредством стандартных методов объекта `Date` с явным учётом локального часового пояса пользователя, что исключает ошибки смещения дат, характерные для метода `toISOString()` при работе в часовых поясах, отличных от UTC.

#### 3.1.5 lucide-react

Библиотека иконок **lucide-react** обеспечивает унифицированный набор SVG-иконок, используемых в элементах навигации, карточках задач и модальных окнах.


### 3.3 Логическое взаимодействие компонентов

В текущей архитектуре Система реализована в виде **монолитного компонента** (`App.jsx`), что обосновано небольшим масштабом проекта и отсутствием необходимости в сложном межкомпонентном взаимодействии. Все состояния, обработчики событий и представления сосредоточены в едином файле.

```
index.html
    └── main.jsx  (точка монтирования, React.StrictMode)
            └── App.jsx  (единый корневой компонент)
                    ├── State Layer (useState)
                    │       ├── tasks         — массив задач, синхронизируется с localStorage
                    │       ├── userApiKey    — API-ключ пользователя, хранится в localStorage
                    │       ├── userName      — имя пользователя, хранится в localStorage
                    │       ├── view          — текущее активное представление ('home' | 'board' | 'calendar' | 'settings')
                    │       └── activeTaskId  — идентификатор задачи, открытой в модальном окне
                    │
                    ├── Side Effects (useEffect)
                    │       └── Синхронизация tasks → localStorage при каждом изменении
                    │
                    ├── API Layer
                    │       └── callGemini()  — асинхронный запрос к Google Generative AI API
                    │                           (fetch POST, структурированный JSON-ответ через responseSchema)
                    │
                    └── View Layer (условный рендеринг по view)
                            ├── Sidebar        — навигационная панель
                            ├── Header         — заголовок, строка поиска, аватар
                            ├── View: home     — форма ввода новой задачи
                            ├── View: board    — сетка карточек задач с фильтрацией
                            ├── View: calendar — интерактивный месячный календарь
                            ├── View: settings — форма настроек (имя, API-ключ)
                            └── Modal          — детальное представление задачи с шагами
```

> [!NOTE]
> При масштабировании Системы рекомендуется произвести декомпозицию `App.jsx` на отдельные компоненты (`TaskCard`, `Sidebar`, `CalendarView`, `TaskModal` и др.) и вынести логику в отдельные хуки (`useTaskManager`, `useGeminiApi`).

## 4. Руководство по развертыванию

### 4.1 Клонирование репозитория

```bash
git clone https://github.com/fromArnur/student-ai-react.git
cd student-ai-react
```

### 4.2 Установка зависимостей

Установка производится посредством пакетного менеджера npm. Выполнение команды воспроизводит точное дерево зависимостей, зафиксированное в файле `package-lock.json`:

```bash
npm install
```

### 4.3 Настройка окружения и конфигурация API-ключа

Система не использует файл переменных окружения (`.env`) в текущей реализации. API-ключ Google Gemini вводится непосредственно через интерфейс Системы в разделе «Настройки» и сохраняется в `localStorage` браузера под ключом `agent_api_key`.

> [!WARNING]
> Ввод API-ключа напрямую через UI означает, что он **не компилируется в бандл** и **не попадает в репозиторий**. Это является намеренным архитектурным решением для защиты ключа при публичном хранении кода.
>
> При необходимости централизованного управления ключом на уровне сборки — добавить файл `.env` в корень проекта со значением `VITE_GEMINI_API_KEY=<ваш_ключ>` и обновить код обращения к переменной: `import.meta.env.VITE_GEMINI_API_KEY`.

### 4.4 Запуск сервера разработки

```bash
npm run dev
```

После запуска сервер разработки Vite становится доступен по адресу `http://localhost:5173` (порт по умолчанию). Адрес выводится в консоли после успешного старта. Режим HMR активен по умолчанию.

### 4.5 Сборка production-версии

```bash
npm run build
```

Результат сборки размещается в директории `dist/`. Директория содержит статические файлы (`index.html`, минифицированные JS и CSS бандлы), готовые к развертыванию на любом статическом хостинге.

### 4.6 Превью production-сборки (локально)

```bash
npm run preview
```

Команда запускает локальный сервер, раздающий содержимое директории `dist/`, что позволяет верифицировать production-сборку до развертывания.

### 4.7 Развертывание на платформе Vercel

Платформа Vercel автоматически определяет тип проекта (Vite + React) и применяет соответствующие настройки сборки.

```bash
# Первичное развертывание (требует авторизации)
npx vercel

# Развертывание в production-окружение
npx vercel --prod
```

Параметры сборки, применяемые Vercel автоматически:

| Параметр | Значение |
|---|---|
| Build Command | `npm run build` |
| Output Directory | `dist` |
| Install Command | `npm install` |
| Node.js Version | 20.x |

## 5. Управление данными и валидация

### 5.1 Модель данных

#### 5.1.1 Сущность «Задача» (`Task`)

Каждая задача в Системе представлена объектом следующей структуры:

| Поле | Тип | Описание |
|---|---|---|
| `id` | `number` | Уникальный идентификатор (Unix timestamp в момент создания) |
| `title` | `string` | Наименование задачи, сформированное моделью ИИ |
| `deadline` | `string` | Дата-дедлайн в формате `YYYY-MM-DD` (локальный часовой пояс) |
| `color` | `'red' \| 'yellow' \| 'purple' \| 'green'` | Приоритет задачи в виде цветового кода |
| `steps` | `Array<Step>` | Массив шагов выполнения задачи |
| `reasoning` | `string` | Текстовое обоснование приоритета, предоставленное моделью ИИ |
| `createdAt` | `string` | Дата создания в локализованном строковом формате |

#### 5.1.2 Сущность «Шаг» (`Step`)

| Поле | Тип | Описание |
|---|---|---|
| `text` | `string` | Текстовое описание шага |
| `completed` | `boolean` | Признак выполненности шага |

### 5.2 Валидация данных через схему API (responseSchema)

В текущей реализации валидация ответа Google Gemini API осуществляется декларативно на стороне самого API посредством механизма **Controlled Generation** (`responseSchema`). Схема передаётся в теле запроса и инструктирует модель возвращать JSON-объект строго заданной структуры:

```javascript
responseSchema: {
  type: 'OBJECT',
  properties: {
    isDeadlineMissing: { type: 'BOOLEAN' },
    title:             { type: 'STRING' },
    deadline:          { type: 'STRING' },   // Формат YYYY-MM-DD обеспечивается системной инструкцией
    priorityColor:     { type: 'STRING', enum: ['red', 'purple', 'yellow', 'green'] },
    reasoning:         { type: 'STRING' },
    steps: {
      type: 'ARRAY',
      items: {
        type: 'OBJECT',
        properties: {
          text:      { type: 'STRING' },
          completed: { type: 'BOOLEAN' }
        }
      }
    }
  }
}
```

Поле `responseMimeType: "application/json"` обязывает модель возвращать валидный JSON. Это исключает необходимость парсинга произвольного текста и снижает вероятность получения некорректных данных.

### 5.3 Валидация на стороне клиента (placeholder)

> [!NOTE]
> **[PLACEHOLDER]** В текущей версии Системы клиентская валидация входных данных от пользователя ограничена проверкой непустоты строки (`inputValue.trim()`). 
>
> При необходимости расширенной валидации форм рекомендуется интеграция библиотеки **Zod**. Пример схемы для валидации объекта задачи:
>
> ```javascript
> import { z } from 'zod';
>
> const StepSchema = z.object({
>   text: z.string().min(1),
>   completed: z.boolean(),
> });
>
> const TaskSchema = z.object({
>   id: z.number().int().positive(),
>   title: z.string().min(1).max(200),
>   deadline: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
>   color: z.enum(['red', 'yellow', 'purple', 'green']),
>   steps: z.array(StepSchema),
>   reasoning: z.string(),
>   createdAt: z.string(),
> });
>
> // Использование при парсинге ответа API:
> const parsedTask = TaskSchema.parse(aiResponse);
> ```
>
> Интеграция Zod обеспечит типобезопасность на этапе выполнения и позволит отлавливать несоответствия структуры данных до их записи в `localStorage`.

### 5.4 Персистентность данных

Система использует `localStorage` браузера как единственное хранилище данных. Запись осуществляется реактивно через хук `useEffect` при каждом изменении массива задач:

```javascript
useEffect(() => {
  localStorage.setItem('agent_tasks', JSON.stringify(tasks));
}, [tasks]);
```

Инициализация состояния при загрузке Системы выполняется через функцию-инициализатор `useState`:

```javascript
const [tasks, setTasks] = useState(() => {
  const saved = localStorage.getItem('agent_tasks');
  return saved ? JSON.parse(saved) : [];
});
```

> [!CAUTION]
> Данные в `localStorage` не шифруются и доступны для чтения любым JavaScript-кодом, выполняемым в том же источнике (`origin`). Хранение конфиденциальных данных (API-ключей) в `localStorage` является допустимым для персональных инструментов, однако не рекомендуется для систем с требованиями к информационной безопасности корпоративного уровня.
